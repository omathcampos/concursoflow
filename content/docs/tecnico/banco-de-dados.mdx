## Tabelas

Schema completo em `docs/03-schema.sql`. As tabelas principais: `profiles` (1:1 com `auth.users`), `subjects`, `topics`, `cycles` + `cycle_entries`, `blocks`, `sessions`, `reviews`, `annotations` — todas com `user_id uuid not null references auth.users(id) on delete cascade`. A partir da fase 10: `notification_prefs`, `notification_log`, `telegram_link_codes`.

Enums: `topic_status`, `block_type` (`teoria`/`questoes`/`revisao`/`lei_seca`/`aula`), `block_status` (`planned`/`done`/`skipped`), `review_status` (`pending`/`done`/`skipped`).

## RLS (Row Level Security)

Toda tabela com dado de usuário tem RLS habilitado, com política `auth.uid() = user_id` cobrindo `select`/`insert`/`update`/`delete`. Isso significa que mesmo um bug na camada de aplicação **não conseguiria** vazar dados de outro usuário — a restrição é aplicada pelo Postgres, não pela query que a aplicação escolhe montar.

Duas exceções deliberadas, sempre acessadas via **service role** (que ignora RLS) dentro de uma Edge Function, nunca pelo cliente do navegador:

- `unsubscribe_token` em `notification_prefs` — o endpoint `unsubscribe` busca a linha por token, não por `auth.uid()`.
- `calendar_feed_token` em `profiles` — o endpoint `calendar-feed` busca o perfil por token, não por sessão.

## Triggers

`handle_new_user()` — dispara em `on_auth_user_created` (Supabase Auth) e cria automaticamente a linha correspondente em `profiles` (e, desde a fase 10, também em `notification_prefs` com os defaults) no momento do cadastro. A função tem `search_path = ''` fixado e `EXECUTE` revogado de `public`/`anon`/`authenticated` — só o próprio trigger do Postgres pode chamá-la, nunca via `/rest/v1/rpc/handle_new_user` direto.

Uma função auxiliar, `notif_local_bounds(timezone, now)`, calcula em SQL (mais confiável que reimplementar em TypeScript) as fronteiras de dia/semana no fuso de cada usuário, convertidas para UTC — usada pelas Edge Functions de notificação pra filtrar blocos/sessões/revisões pelo fuso correto. Só `service_role` pode executá-la.

## Migrations

Toda mudança de schema é uma **migration versionada** (`supabase migration new nome`), nunca SQL avulso rodado direto no dashboard. Cada migration é registrada em `MIGRATIONS.md` no mesmo commit: arquivo, descrição, data, ambiente e a fase correspondente. Migrations aplicadas são **imutáveis** — uma correção sempre vira uma migration nova, nunca uma edição retroativa de uma já aplicada.

Segredos (`RESEND_API_KEY`, `TELEGRAM_BOT_TOKEN`, `CRON_SECRET`) nunca entram em arquivo de migration versionado — vivem em `supabase secrets` ou, no caso do `CRON_SECRET` referenciado pelo agendamento do `pg_cron`, em `vault.decrypted_secrets`.
